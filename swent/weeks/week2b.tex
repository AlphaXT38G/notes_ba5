\section{Breaking the Dependency}

\begin{center}
\includegraphics[width=\linewidth]{images/repository-interface.png}
\end{center}

\begin{keybox}[title={Program against an interface, not a concrete class}]
\begin{itemize}[leftmargin=1.5em, itemsep=3pt]
  \item \textbf{Before} --- the ViewModel calls \texttt{FirebaseFirestore} directly. There is nothing to substitute: production code and test code are the same code.
  \item \textbf{After} --- the ViewModel depends only on a \texttt{UserRepository} interface. \texttt{FirestoreUserRepository} implements it for production; \texttt{FakeUserRepository} implements it for tests.
\end{itemize}
\tcblower
This is what makes stubs, mocks, and fakes possible in the first place: you can only inject a test double where the code depends on an interface, not a hard-coded implementation.
\end{keybox}

\begin{warnbox}[title=The Firebase emulator is not a test double]
The emulator runs a \textbf{real} Firestore implementation locally --- same query engine,
same security rules --- just not in the cloud. It is not a fake: a fake replaces Firestore
with a few lines of your own code that only approximate its behavior.
\end{warnbox}

\begin{center}
\renewcommand{\arraystretch}{1.3}
\begin{tabular}{@{}l p{4cm} p{4cm} p{4cm}@{}}
 & \textbf{Fake} \textit{(in-memory)} & \textbf{Emulator} \textit{(real Firebase, local)} & \textbf{Real Firebase} \textit{(cloud)} \\
\hline
\textit{speed} & milliseconds & seconds & seconds + network \\
\textit{checks} & your own logic & your queries and security rules & nothing you should be unit-testing \\
\textit{use for} & unit tests (hundreds of them) & integration tests (a handful) & never in CI \\
\end{tabular}
\end{center}

\section{Test Doubles}

\begin{center}
\includegraphics[width=\linewidth]{images/three-test-doubles.png}
\end{center}

\begin{defnbox}[title=Three test doubles]
All three replace a dependency; they differ in what you assert against.
\begin{itemize}[leftmargin=1.5em, itemsep=3pt]
  \item \textbf{Stub} --- answers questions with a canned value, no logic. You never ask it anything afterwards; you assert on \textbf{your own code's result}.
  \item \textbf{Mock} --- answers, and remembers every call (arguments, how many times, \ldots). You assert on the \textbf{calls your code made to the mock}.
  \item \textbf{Fake} --- a small working thing: a real, simplified implementation (e.g.\ an in-memory map instead of a database). You assert on \textbf{your code's behavior over a sequence of interactions} with the fake.
\end{itemize}
\end{defnbox}

\begin{center}
\includegraphics[width=\linewidth]{images/test-doubles-example.png}
\end{center}

\begin{exbox}[title=Picking the right double]
\begin{itemize}[leftmargin=1.5em, itemsep=3pt]
  \item[(a)] \textbf{Stub} --- checking that the ViewModel shows an error message on sign-in failure only cares what your code does with a failure, not how the failure was produced.
  \item[(b)] \textbf{Mock} --- ``a failed sign-in is reported to analytics exactly once'' is a claim about the \emph{conversation} itself; only a recorder can check it.
  \item[(c)] \textbf{Fake} --- a cart flow that reads and writes twenty user documents, where order matters and later reads depend on earlier writes, needs a real (if tiny) implementation --- ten lines of an in-memory map.
\end{itemize}
\end{exbox}
